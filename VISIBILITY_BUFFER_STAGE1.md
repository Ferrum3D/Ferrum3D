# Stage 1 contracts and validation

The forward depth/opaque renderer remains the active comparison path. Stage 1 adds core and material plumbing; it does not enable visibility rasterization, surface evaluation or deferred lighting for sample materials. Those shaders and sample material ports belong to stages 2–4.

## Shared contract, version 1

`Shaders/Passes/Visibility/Contracts.h` is shared by C++ and HLSL. Visibility is an unfiltered `R32G32_UINT` attachment, cleared with `ColorClearValue::Uint(0)`. X is the persistent `MeshInstanceTable` row plus one; X zero is background. Row `0xffffffff` is reserved. Y is `(meshlet << 6) | primitive`, with 26 meshlet bits and six local triangle bits. The meshlet triangle limits are asserted against Core. Group publication validates cooked LOD meshlet counts; instance allocation validates the reserved row. Coverage must explicitly output these IDs per primitive, preserving the packed source winding.

The surface uses separate `R32_UINT` images. G0 is sRGB-encoded RGB8 in bits 0–23 and the model ID in bits 24–31. G1 is two signed 16-bit octahedral coordinates, including the negative-Z fold. G2 has roughness, metallic, AO, and flags in successive bytes for StandardPBR; SimpleLit reserves the first three bytes. G3 packs nonnegative scene-linear emissive as R11/G11/B10. Flag bit zero means the extended payload was written. Clear only G0 to zero; covered pixels write G0/G1/G2, and consumers read G3 only with the valid flag. Encoding/decoding and material evaluation will be implemented in stage 3.

Shading routes are assigned from the deferred shader and its defines; there are no predefined SimpleLit/PBR IDs. Zero is background and 255 is the unsupported route. The compact eight-bit surface route requires a per-view mapping and an explicit overflow policy when the surface passes are implemented. The GPU material table carries independent 32-bit evaluation and shading pipeline slots. Surface evaluation groups use `MeshGroupTable` rows, which identify one geometry/material binding. Transforms and instance parameters remain lane-specific. Tile width is 128; local pixel commands use seven bits per coordinate and two reserved bits. Wave commands contain four 32-bit fields: tile, group, pixel offset and valid count. Width defaults to 32 logical lanes, with group-uniform correctness independent of hardware wave width. `VisibilitySupport::Query` chooses an explicit supported 32/64 wave lane count only when control is available; callers put that request in `ComputePipelineDesc::m_waveLaneCount`, which participates in the cache key. Cross-lane operations are baseline requirements on RDNA2+/Turing targets, not individual capability switches.

## Material API and routing

`Material:technique('SurfaceEvaluate', ...)` and `DeferredShade` create compute descriptions. Set `computeShader` and any shader defines. Shading interpretation is defined by the shader; surface flags are shader-written payload data. Graphics shaders, render targets, depth and raster/blend state are rejected on compute techniques. `DepthVisibility` remains graphics. Existing graphics descriptions and specializer/permutation keys retain their behavior. Shader defines are sorted and passed through to reflection and pipeline creation.

Runtime parameter reflection merges every consuming graphics/compute shader and asserts layout agreement. Parameter-free shaders work without a reflected parameter struct. The runtime exposes compute pipelines by role and does not require an evaluation/shading pair. `MeshSceneModule` owns separate evaluation and shading `ComputePassRegistry` tables, like its existing graphics pass routing. Tables retain pipelines and assign append-only scene-local slots, deduplicating cached shader/define PSOs independently in each pass. The parameter allocator only manages parameters. Material rows carry the parameter pointer and both routing slots; a missing role uses an invalid slot. Later pass builders may refine each pipeline bucket by its consuming parameter values; evaluation and shading never share a combined grouping key. Legacy materials deliberately retain invalid deferred routes until their stage 3 ports.

## Frame lifetime and resource requirements

From coverage through evaluation, each view must see one immutable instance/group/LOD/material snapshot. Retain its database pages, material allocation pages, device-address geometry, texture descriptors and asset generations through the frame fence. Reload, stream-out and row recycling must not overwrite that snapshot. Stage 1 establishes this contract and stable registry ownership; extending existing mesh resource declarations/retention to the new consumers is required when those passes are wired in stages 2–5.

Declare argument generation as compute UAV writes and indirect consumption with `PassIndirectArgs`; Core now accepts that binding on compute passes and emits its existing execute-indirect/command-read barrier. Arguments contain three uint32 counts. The effective buffer offset must be four-byte aligned with 12 bytes remaining in the bound slice. Direct and indirect dispatch share Vulkan compute state setup.

`GetFormatCapabilities` reports image format usages and `VisibilitySupport::Query` checks visibility, surface, sampled D32 and HDR support. Packed HDR is preferred; RGBA16F adds four bytes per pixel. Keep resource creation and depth/material format changes together in stage 2. Typed color clears preserve float, signed integer and unsigned integer bit patterns. Vulkan attaches only aspects actually present, enabling D32 without a stencil attachment.
